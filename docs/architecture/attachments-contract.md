# Conversation attachment contract

The authenticated owner uploads raw bytes to POST /api/attachments?filename=…, with exact Content-Type. Origin and session checks precede this route's bounded body read. This route alone permits10MiB; ordinary API mutations retain1MiB. Returned metadata is {id,filename,mimeType,sizeBytes,sha256,state:'uploaded'}, never local paths or file bytes. GET /api/attachments/{id} is an authenticated no-store/nosniff attachment download. DELETE refuses bound files, including uncertain submissions.

Supported attachments: PNG/JPEG/WebP signatures, PDF framing, strict UTF-8 plain text/Markdown/CSV, valid JSON, and modern Office DOCX/XLSX/PPTX. The shared picker supplies canonical MIME types even when the browser provides an empty or generic type. Office upload validation checks the matching package structure and bounds decompression/XML parsing; it rejects malformed, encrypted and macro-bearing packages. Older DOC/XLS/PPT need conversion to DOCX/XLSX/PPTX or PDF. Active HTML/SVG and unknown binaries are rejected. Signature validation is not a claim that arbitrary malformed image payloads can be decoded. Maximum10 files and10MiB combined per message. Stored uploads are capped128MiB with a224MiB database upload guard (independent of the1GiB product backup ceiling). Additive SQLite attachments bytes are included in existing encrypted/private backup workflows; optional schema compatibility preserves old archives. Local Coding materializations are private, hash-checked atomic files reconstructed from the DB after restore.

Message attachmentIds bind immutable IDs/hashes into the existing exact request fingerprint. Binding precedes native dispatch; outcomes that may have been sent retain the file. Text stays byte-for-byte unchanged as the user input. Native Coding and the version-pinned original IDE owner receive typed localImage inputs. Document text and metadata use additionalContext kind=untrusted beside mandatory agent-protocols. Neither attachment paths nor uploaded contents can override workspace, model, approvals or sandbox settings. Owner start and steer use the pinned existing native input contract; no original build-session test messages are sent.

Coding PDFs use fixed /usr/bin/prlimit + /usr/bin/pdftotext,256MiB address-space/6 CPU-second/8 wall-second limits, at most100 pages/400001 output bytes, then a100000-character aggregate reference budget. Failed/empty text extraction refuses dispatch explicitly; scanned PDFs require OCR outside this slice or uploaded page images. Truncation and the first100-page boundary are identified in model context. These dependencies must exist on the deployment host. Companion extraction and vision are owned by the native runtime; its default subscription provider needs the accompanying image-conversion and model-vision registry fixes.

Companion, Today and Goals item chats all use the Companion adapter: original attachment bytes and MIME are forwarded to IronClaw's document extraction/vision pipeline. Coding and Updates ticket chats use the Coding adapter: images become native Codex image inputs; document text and the immutable original file path become untrusted reference context. Codex is not expected to natively decode an arbitrary Office upload from the browser.

Coding Office extraction reads document text, spreadsheet cell values and slide text into the existing aggregate reference budget, with truncation identified. It does not execute macros, recalculate formulas, follow external relationships or perform OCR. Cached formula results can be stale or absent; extracted text is not a lossless rendering of formatting, charts, drawings or embedded media. Original documents remain available for download and explicit further inspection.

Shared paperclip UI exposes previews, download/remove, upload state and failures. Draft metadata survives tab navigation/reopen, while pending uploads abort on unmount. Each send saves its attachment IDs before the first await and clears only accepted IDs. Uncertain delivery never replays automatically. Active attachment and voice sibling keys are distinct. Accepted Coding history gains local metadata on exact receipt turn IDs, without client history polling per file. No filebytes enter browser persistence, Git or operational receipts.
