# Daily agenda

The agenda reads canonical commitments/progress and saved calendar windows; it does not replace `/today`, copy commitments, or contact providers during reads. A date and validated IANA timezone define the planning scope. Consecutive local midnights produce the day window, including 23/25-hour DST days. Timed events overlap that window; zero-duration timed events appear when their instant is inside its inclusive-start/exclusive-end bounds. Provider all-day dates retain date semantics.

`GET /api/agenda?date=YYYY-MM-DD&timezone=Europe/London&offset=0&limit=50` returns date/timezone, window, observedAt, sources, commitments, events, emails, totals, partial and nextOffset. Page size is 1–100. Pagination traverses calendar chronology, up to 20 source-supported actionable recent inbox messages after non-actions from the shared100-source aggregate overview are filtered, then the canonical commitment list, split into the three response arrays; use the returned nextOffset. Counts cover the entire eligible source set. Concurrent source changes require a refresh; offsets are not a frozen transaction across pages.

Each item has an opaque stable key and `triage: {revision, disposition}`. Commitment fields, including id/revision/date/log, match the existing domain caller. Events contain calendarId/eventId/title/start/end/allDay/url/syncedAt. Sources distinguish account connection from calendar-list synchronization and snapshot coverage/freshness. Calendar states are not_connected, not_synced, partial, stale or current; per-calendar state additionally includes error. Coverage is none/partial/complete. Current means the saved list and full day windows are at most 15 minutes old, not that a live provider push has occurred. Errors retain previous data and produce partial aggregate state; an empty partial result does not establish free time. The Calendar page retains the explicit provider-read sync workflow. Email is not_connected with mail_consent_not_granted until separately authorized mailbox access exists; calendar grants never imply mailbox access. The injected mailbox adapter reads encrypted local snapshots only. `sources.email` reports overall state, per-account consent/freshness/error and truncation without duplicating message arrays. Email items expose exact account/message/thread IDs, subject/from/snippet/receivedAt (ISO 8601), unread/important source labels, source URL, syncedAt (Unix seconds), sourceState and local triage. They represent the current cached recent inbox (last 30 days), independently of the selected planning date; that date scopes choices, not a historical mailbox reconstruction. Sync remains an explicit Settings action.

`PUT /api/agenda/triage` accepts date/timezone/key/revision/disposition, where disposition is focus/later/dismissed/none. It returns key/revision/disposition. Unsaved choices have revision 0 and disposition none; every write increments the optimistic revision. Source keys must match eligible canonical items and are checked again before commit. Choices are scoped by day and timezone. They do not complete, pause or delete commitments, move deadlines, change reminders, or edit/cancel provider events or change mailbox state. Email membership and access are rechecked against the encrypted canonical cache inside the local write transaction. Resetting to none preserves revision history; removed source annotations remain inert and are never reconstituted into canonical records.

`GET /api/agenda/chat` with the same date/timezone reads an existing thread binding without creating one. `POST /api/agenda/chat {date,timezone}` reserves a durable action ID and creates/reuses one native Companion thread for that exact tuple. Lost responses retry the same native creation action; concurrent requests converge through native idempotency. A title is display metadata, never binding authority. Opening a chat does not send a model turn. Confirmed Companion deletion retires only its matching daily binding; opening that day again reserves a new creation action. Replaying an old deletion cannot remove a replacement binding. Admitted action/audit receipts remain intact.

On each new Companion message, its server-owned reverse binding loads fresh saved-source agenda state. The agenda reference is at most 2 KiB of serialized UTF-8 inside the existing 8 KiB aggregate run reference. Focus choices are admitted first; partial and titlePartial metadata expose omission/truncation. It carries canonical IDs/revisions and progress where admitted, plus email state/freshness/truncation and exact cached message identity. Email subjects are untrusted source data; snippets and bodies are excluded from the daily Companion reference. The separate explicit mail classifier may receive bounded saved snippets, as described below. HTTP and Companion use the same injected agenda service. User text is stored unchanged. An uncertain retry reuses the originally admitted request/context; it never rereads facts and changes that request. Existing summaries/history can still contain older facts. The runtime selected main model and approval policies remain unchanged. Agenda reads and Companion-reference assembly do not start another model. Explicit mail triage and successful sync may start the bounded classifier described below; neither flow grants provider-write or additional memory authority.

Source tests cover authenticated HTTP callers, source/error provenance, DST/instant/all-day filtering, pagination, scoped CAS local-only edits, native creation receipt retry, current per-turn data, unchanged replay and Unicode byte admission. Browser/mobile integration and deployed acceptance are separately recorded by the integration owner.

## Always hide a calendar entry locally

`PUT /api/agenda/calendar-visibility {key,revision,hidden}` persists a local preference for the exact calendar ID and provider event ID represented by the server's `calendar:` key. Initial visibility is `{hidden:false,revision:0}`; every accepted change increments the revision and returns key/hidden/revision. Unknown or no-longer-cached sources cannot be newly hidden. Stale revisions fail with 409. Undo (`hidden:false`) remains possible for a known preference even if the event left the saved snapshot. A revision tombstone prevents an old Hide button from silently undoing a later Show again.

This preference has no planning date or timezone. It survives app restart, calendar refresh, renamed/moved entries retaining the same identity, and changing the viewed day. Recurring entries are matched by the exact provider occurrence ID: there is no series-prefix matching or implicit whole-series action. Matching titles, or identical event IDs in another calendar, do not share preferences. Provider calendars, events, reminders, daily triage and audit records are unchanged. There are no provider calls when hiding, listing preferences or restoring visibility.

Default `/api/agenda` excludes hidden entries before pagination and includes `hiddenEventCount` for matching entries on the selected day. Every returned event includes its visibility object. `includeHidden=true` includes hidden entries with their visibility flags for explicit inspection. Totals describe the returned eligibility set. The fresh daily Companion reference follows default visibility and reports the hidden count; existing admitted requests and transcript history remain unchanged, and explicit canonical calendar reads still expose the original provider records.

`GET /api/agenda/calendar-visibility?offset=0&limit=50` lists hidden preferences across dates (limit 1–100), returning items/total/nextOffset. Items include key/calendarId/eventId/title/calendarName/hidden/revision/updatedAt/sourceAvailable. The display label comes from the current saved source when available, otherwise the bounded label saved when hidden. This supports Show again outside the current calendar window or after local source removal. Preferences are installation-local settings and can be restored with its database backup; they never modify the remote calendar.

Focused rows across source kinds precede other rows before pagination, preserving the existing deterministic order within each group. Clients restart pagination after changing triage to avoid cursor drift.

Today renders Focus as a prominent dated priority list with completion and source-open actions. A successful local triage receipt updates the card, announces the saved choice, and opens the priority location for the same active day. Refresh uses canonical pagination; it never resends the choice. Loaded priorities are explicitly partial when more pages remain. Focus does not send mail, edit calendars or complete commitments implicitly.

Today is a navigable app with Plan, Schedule, Inbox, Chat and Boards pages sharing a selected date, timezone and cached agenda snapshot. Plan holds Focus and commitments; Schedule shows calendar items; Inbox separates actionable email from review; Chat has a dedicated conversation viewport. Boards reads all canonical capacities and commitments independently of the agenda date, with list, Kanban and explicit-date Gantt views (see capacity-boards-contract.md). Page navigation preserves the selected day and follows browser history; unrelated anchors do not reset that scope. Completed, deferred, source and hidden-entry panels remain separate disclosures. Leaving Chat stops microphone capture and closes its live stream without discarding the conversation.

## Email actionability

Only `actionability.state=action` messages enter Agenda totals, pagination, Focus eligibility and fresh Companion grounding. Existing local triage choices remain stored if an item becomes ineligible. The new input must be classified before it can reappear. Source state and `classification` counts distinguish missing mail consent, unsynced/stale mail, pending classifications, review, and excluded mail; an empty action list is not proof of an empty inbox.

`POST /api/email/triage` returns 202 with `{classification,items,truncated}` and starts or joins bounded background work on the currently saved source window. `GET /api/email/triage` has the same response and performs no provider/model work. A successful explicit mail sync or rebuild also requests classification. Multiple requests while busy coalesce into one pending fresh pass. Navigation never initiates classification. Classification state is `running`, `error`, `unclassified` or `ready`, with counts `action/ignore/review/pending`, source `limit` 100, `actionLimit` 20, `completedAt`, generic `error` and explicit limited-mailbox scope. A process restart does not resume a background request automatically; source-bound cached decisions remain available and an explicit request can reconcile unfinished work.

Each item has advisory `actionability`: state `action|ignore|review`; kind `reply|todo|null`; basis `explicit|implicit|null`; short `reason`, `action`, exact source `evidence`; `classifiedAt` and `pending`. Unknown/duplicate model IDs, malformed schema, unverifiable quotes, missing context, or unverified reply status fail to review. Spam/trash and list/bulk mail are excluded before inference. The main model evaluates other intent, including cold outreach; unread/important labels are never sufficient evidence. No-reply transactional messages may still contain real obligations. No tasks, replies or provider changes are created automatically.

Sync preserves bounded labels and list markers, fetches metadata-only thread IDs/labels/timestamps, and keeps the latest retrieved message per thread. Normal sync is bounded to 30 seconds and at most one list, 20 message and 20 thread requests. Explicit `POST /api/email/accounts/{account}/rebuild` is bounded to 120 seconds and at most one list, 100 message and 100 thread requests. It atomically replaces only Leam's encrypted snapshot, invalidates the old derived decisions with a new local generation, and starts classification; failure retains the previous saved view. A verified newer outgoing reply or unknown thread state prevents a reply classification from becoming an action. A separate todo requires its own source evidence. Large, unavailable or malformed thread metadata remains unverified. This is a saved snapshot, not a claim of continuously current reply state. No message bodies or attachments are fetched; truncated snippets may require manual review.

Classification calls the selected main model through the runtime's non-streaming prepared-context OpenAI-compatible route with an explicit strict JSON schema and empty tools. `tool_choice` is omitted because that route rejects it without tools. The prepared run has no ambient tool catalog or Companion transcript. It retains runtime run evidence. Mail is untrusted user data separated from host policy; classifier output grants no execution authority. Batch limits are five items and 14 KiB serialized source data, with 24 KiB accepted decision text, 128 KiB accepted HTTP result and a 300-second operation timeout. Provider generation ceilings remain the runtime profile's own limits; no unsupported token-limit claim is made. Requests use deterministic input/grant/model/policy-bound idempotency keys; there is no conversational fallback or automatic transport retry.

Decision caches are encrypted installation settings using their exact key as authenticated associated data. They bind exact account/message input hash, current consent grant and policy version. Commit rechecks current scope, grant and source under one database transaction. Changed input or grant invalidates old outputs. Account/provider/mail removal deletes only affected caches. Corrupt derived evidence remains preserved, excludes that mailbox's decisions, and reports a diagnostic without blocking other mailboxes. Backup admission validates decision ciphertext and envelope shape.

The daily reference remains at most 2 KiB inside the existing 8 KiB aggregate request context, with exact source identities, freshness/counts and short action kind/action/reason. Evidence quotes and mail snippets are available through the authenticated review response, not added to automatic grounding. Existing admitted-message retries retain their original context.

Action inbox UI admits only email items whose server actionability state is action and applies the 20-item cap after filtering. Ignore/review/pending messages remain outside the priority/action feed; a collapsed read-only review uses GET /email/triage and source links. Missing classification says Not triaged yet, never No actions needed. Explicit POST /email/triage starts/joins classification; the UI polls status with bounded GETs and never repeats the POST on reconnect. Rebuild action inbox explicitly replaces Leam's saved source/decisions and scans farther; its copy states that Gmail is unchanged and does not promise 20 results when fewer clear obligations exist. Suggested action, reason and explicit/implicit basis are displayed as untrusted plain text. Classification does not send mail or grant any provider-write authority.

Each classifier batch revalidates current mailbox existence, OAuth client binding, consent grant/scope/state and exact saved input immediately before admission, including after provider lookup or previous model calls. Changed or removed sources cannot enter later requests; already admitted requests cannot be recalled. The same authority/source check runs before persisting a result. Disconnecting mail removes derived decisions and does not replay classification.

Saved-mail inspection separates Needs review, Excluded and Not yet classified into independently collapsed groups. Needs review contains only classified uncertain messages; pending messages have their own group. Expanding a group lazily reads the saved triage response and reuses it for other groups. Source refresh retires an in-flight read before replacement; no model or provider operation starts from disclosure alone.

Classification, status/review counts and Agenda eligibility share the same bounded retrieved overview. Ordinary per-account sync remains capped at 20; explicit rebuild reads at most 100 per account; the aggregate overview remains capped at 100 and exposes truncation for additional cached or provider records. Every source in that overview is considered, including later accounts. Five-item/14 KiB batches and the 300-second operation timeout remain unchanged. Timeouts retain verified decisions and report pending sources; a later explicit request skips valid cached hashes. No additional provider scanning is introduced by classification.

## Explicit review of saved mail

Authenticated same-origin `PUT /api/email/triage/review` accepts `accountId`, `messageId`, `reviewRevision`, `decision` (`action` or `ignore`), `kind` (`reply`, `todo` or null), and `action`. Adding to Today requires an explicitly confirmed nonempty action label (at most 240 characters) and kind. Exclusion requires empty action and null kind. Unknown fields are rejected. The owner may intentionally override model review or exclusion without a source quote; the stored choice is attributed to that owner, not to independent verification.

`GET /api/email/triage`, account snapshots and eligible Agenda items expose an opaque `reviewRevision` over the current source, consent grant, policy version and cached decision generation. The write rechecks current cached membership, exact source, configured OAuth client, actual read-only scope, connected mail state and revision in one transaction. Changed or removed state returns 409 and requires a fresh read/confirmation. Corrupt derived evidence remains unmodified and cannot be reviewed until repaired. A lost response is reconciled by reading current state; no client may automatically replay an edit with a new revision.

The receipt is `{accountId,messageId,reviewRevision,actionability}`. Encrypted decisions add `reviewedBy: user` and `reviewedAt`, with `basis: null`, empty evidence, and the fixed reason `Explicit user review; not independently verified`. A valid human decision cannot be overwritten by an already-running model result. Another explicit owner edit requires its new revision. Changed source, grant or policy invalidates the decision as before. The bounded daily reference carries the human attribution alongside its short action; no model-verification claim is introduced.

Add to Today makes an eligible saved message an Action inbox item. It neither sets Focus nor creates a commitment, reply, or mailbox change. Focus remains a separate day-scoped choice. Exclude removes the message from current action eligibility while preserving its source and any existing local day choice for later review.

Owner mail review offers Add to Today with an explicit action label and reply/task choice, or Exclude. It submits the exact source review revision and waits for the server's matching human-review receipt before announcing success and refreshing the canonical view. Approved actions appear in Action inbox with user attribution; Focus remains a separate deliberate day-local choice. Errors keep the edit draft and instruct a status refresh before retrying; no reconnect/timeout automatically repeats a review mutation. No Gmail write or commitment creation is implied.

Explicit rebuild resets that mailbox's derived classification and owner mail-review choices only after a successful provider read. The Today confirmation names that reset; cancellation sends no request. Ordinary sync preserves source-bound owner decisions when unchanged. The combined overview/classifier remains capped at100 across accounts, and its truncation flag reports additional cached or provider results. Rebuild does not promise20 actions or modify Gmail.

## Companion Focus retrieval and proposals

`leam_today` now accepts an explicit `view=agenda` with required `date` and IANA `timezone`, optional `focusOnly`, and existing `limit`/`offset` pagination. Its default `view=commitments` keeps the prior commitment/progress response. Agenda mode reads the same injected saved-source service as Today, including local Focus/later/dismissed/none choices. Returned items contain exact source IDs, full labels, canonical record/progress revisions and daily triage revisions. `focusCount`, total, partial and nextOffset describe the selected eligible set; sourceState and per-item syncedAt distinguish saved/stale data from live provider knowledge. Hidden calendar entries remain excluded. No mail body/snippet/address or commitment notes are included, and all labels remain untrusted reference data. Reads never classify mail, contact providers, create proposals or mutate records.

The bounded per-turn dailyAgenda adds focusCount and a leam_today readMore descriptor. A truncated initial reference therefore points to a retrievable canonical page; missing reference items do not imply an empty Focus list. The existing2KiB daily/8KiB aggregate budgets and admitted-request retry identity remain unchanged.

`agenda.triage` is available through leam_operation_schema and leam_propose. Input is the existing date/timezone/key/revision/disposition schema. Review shows the current source title and daily choice. Execution uses Agenda.triage, and the saved completion receipt commits in the same transaction as its existing source-membership and optimistic revision checks. A changed source/revision fails rather than overwriting a newer choice; repeated completed approval returns the same receipt. This supports moving into/out of Focus, Later or Dismissed, not assigning an order within Focus, changing provider state, completing a task, or adding a reminder.

A proposal naming a bound Today thread must match that server-owned binding's date/timezone. Trusted internal Today-origin calls additionally require that binding and follow the configured Today approval setting. Generic MCP has only an installation tool credential and no runtime-attested originating turn, so a model-supplied threadId cannot activate automatic Today approval: these proposals remain pending for the existing Approvals flow. No approval preference changes occur. Conversational automatic approval requires a separately authenticated runtime-origin seam; it is not claimed here. The existing leam_today/propose tool names remain within the deployed capability ceiling, but runtime MCP schema discovery must refresh after deployment.
