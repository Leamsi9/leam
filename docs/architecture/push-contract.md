# Phone push

Leam uses standard encrypted Web Push. The API's push worker scans durable reminder revisions and persists per-device delivery receipts. Encryption uses pywebpush 2.5.0 AES128GCM and py-vapid signing; Leam controls the HTTP transport, timeout and retry behavior. HTTPS endpoints are restricted to Chrome/Firefox/Safari push services, with no embedded credentials, custom ports, redirects or ambient proxy use. Unsupported browsers fail registration explicitly.

Settings exposes the operator contact address, browser permission/registration, named devices, test notifications, removal and recent delivery outcomes. Permission is requested only from the Enable button. iOS/iPadOS requires opening the Home Screen app. The private subscription endpoints and key material never appear in status responses. Lock-screen messages contain generic text; clicking opens Today. Signing out leaves an explicitly registered device subscribed to generic notifications until removed or browser permission is revoked.

VAPID identity is written privately, fully flushed, and atomically published without replacing a concurrent initializer's identity. Backups must include `push-vapid.pem` alongside SQLite subscription records. Never regenerate that key as routine recovery: existing subscriptions bind to it.

Each reminder ID/revision/device combination has one durable delivery identity. Workers lease queued deliveries before network I/O; a crash or uncertain network outcome retries after the lease. Stable browser notification tags and push topics collapse repeated attempts where supported, but this is at-least-once delivery. A snoozed reminder becoming due has a new revision. Completion/withdrawal and device removal cancel outstanding work; already accepted/in-flight notifications cannot be recalled. Pending delivery expires after one hour. HTTP 404/410 expires only the exact subscription that was used, preserving a replacement registered during the request. Transient responses and network errors retry; other responses are visible failures. The independent recovery/deployment slice will supervise this worker as part of the API.

Provider acceptance does not prove device display. Status says so explicitly. Only an explicit user confirmation of a test records observed receipt. Tests inject a synthetic push event into full Chromium and inspect its notification registry; that is service-worker coverage, not an external push-service or phone acceptance claim. Actual HTTPS/phone delivery remains a final acceptance requirement.

Primary references: [pywebpush](https://github.com/web-push-libs/pywebpush), [Apple Web Push requirements](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [Mozilla Autopush endpoint](https://mozilla-services.github.io/autopush-rs/), [iOS Home Screen Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).
