# Connected account boundary

Leam owns personal account connections through provider adapters independently of IronClaw's model/runtime credentials. The first adapters are Google Calendar and Microsoft Graph. Current implementation provides application setup, account authorization, refresh, access verification, reconnect and local disconnect. Calendar snapshots and reviewed commitment-to-event creation are implemented; inspection and conditional editing/removal of supported linked events are implemented. Authorization success must not be presented as successful calendar sync.

OAuth uses Authlib 1.8.0 (HTTPX2 transport) with authorization code and S256 PKCE. Provider authorization/token/profile endpoints are fixed; authenticated API calls enforce exact provider HTTPS hosts. Environment proxies and redirects are disabled. Application setup and all non-callback routes require Leam authentication and same-origin mutations. The exact provider callbacks are public GET routes because the Leam session cookie uses SameSite=Strict. State is random, hashed in SQLite, single-use, expires after ten minutes and is tied to a still-valid initiating session and provider. The session/configuration are checked again after token exchange. No ID-token claims are trusted: identity comes from the provider's authenticated profile API.

Provider configuration has optimistic revisions. Per-provider locks serialize configuration, authorization completion, token refresh and disconnect in the single-worker deployment. Disconnect cancels pending authorizations for that provider so an older consent flow cannot recreate a removed account. Application removal deletes its current connections/configuration and pending flows. Local deletion does not revoke the external provider grant or erase historical backups; the UI says so. Revocation can be managed in provider account permissions.

Client secrets, tokens and pending PKCE material are authenticated-encrypted with AES-GCM, binding ciphertext to its record identity. The private installation key is atomically published after fsync in `accounts-key`; never silently rotate it. Backup/restore must preserve this key and the SQLite database together. Runtime/API logs must omit query strings on callbacks and must not log OAuth request/response bodies. Global validation errors retain safe field/error descriptions without the submitted input, including passwords and oversized secrets.

Refresh-token replacement is persisted before subsequent API access. Invalid grants expose a reconnect state; network/service failures preserve the prior connection and last verification time. Account verification is separate from calendar data freshness. Required provider credentials/consent are supplied through the UI; no existing source app account stores are copied. Google setup requires a Web OAuth application and Calendar API; Microsoft setup uses a Web redirect and appropriate organizational/personal account support. The settings show the exact callback URL and requested scopes.

Tests exercise both provider flows with controlled protocol fixtures, state replay/provider mix-up/expiry/logout, encryption/no secret echo, refresh rotation, configuration concurrency, URL credential boundaries and pending-flow cancellation. These do not prove real Google/Microsoft connectivity. The live mobile setup test uses synthetic application credentials and does not contact a provider.

Primary references: [Authlib OAuth client and PKCE](https://docs.authlib.org/en/stable/oauth2/client/http/index.html), [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Microsoft authorization code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).

## Calendar snapshots
Calendar lists and bounded event windows are cached separately from account verification. Synchronization follows complete provider pagination (45 seconds, at most 20 pages/5000 entries); partial, malformed, cross-target and failed fetches retain the previous complete snapshot and expose a failure beside its original timestamp. Microsoft next links must retain the exact initial API origin/path; Google page tokens are passed to the fixed original endpoint. Event windows require explicit offsets and a positive span of at most 31 days.

Google recurring occurrences use singleEvents; Microsoft uses calendarView. Timed events normalize to UTC; Graph reads request UTC and unexpected timed response zones fail instead of guessing. All-day events retain provider date components and exclusive end dates rather than shifting dates into the viewer timezone. Multi-day all-day display includes the full date span. Actual provider all-day semantics still need verification with the user's account during live acceptance. Disconnect cascades through account-owned calendar snapshots.

The mobile Calendar page exposes source identities, list/event freshness, chosen refresh range and the actual saved range. Date-input changes do not relabel old data as newly synchronized. Calendar creation is a separate explicit preview/confirmation workflow.


## Reviewed event creation
Active commitments can be scheduled into writable calendars. Preview binds the exact commitment revision, calendar identity/name, title, local time, timezone, offset and elapsed duration into a digest. Nonexistent DST times fail; repeated times have an explicit first/second occurrence selector. Changes between preview and first submission require another review. Creation contains no attendees and does not send invitations.

Before contacting the provider, SQLite reserves the request ID, reviewed data and exact provider payload. Retries use that stored payload even after a commitment edit, process restart or account disconnect/reconnect. Google receives a deterministic event ID and private Leam action marker; a duplicate conflict is reconciled by reading and checking the marker. Microsoft receives a stable transactionId. Completed receipts are available without a live account. Provider-side deduplication is covered by fixtures and still requires real-provider acceptance. No automatic retry makes a new action ID.

The mobile UI retains submitted requests across reloads and discovers server reservations, prioritizing unresolved actions and paginating history. It hides the original creation confirmation after submission and offers recovery of the same request. A definitive rejection before reservation carries X-Leam-Action-Reserved: no, allowing the UI to discard only that unsubmitted attempt and obtain a fresh preview. Calendar writes mark an existing snapshot stale until it is explicitly refreshed.

Action receipts intentionally survive account disconnection and calendar-list removal, preventing a previously used ID from becoming a new write. These records contain calendar/commitment review data, never OAuth credentials. Future retention controls must preserve retry tombstones when purging personal action history. Deployment is single-worker; per-action in-process locks serialize concurrent repeats.


## Linked-event inspection and changes
Leam-created personal timed events can be inspected live, edited, or removed from the mobile UI. The inspected provider ETag is carried unchanged through preview and explicit confirmation to the conditional PATCH/DELETE. The current event is read again before mutation. Events with attendees, external organizers, recurrence, missing versions, or conversion to all-day are blocked and linked to the provider UI. The shared TimeBlock validation handles DST gaps/folds for both creation and editing; inspection preserves the original event timezone and fold in editor defaults.

Changes reserve exact requests/payloads in SQLite before mutation. Only one unresolved change per linked event may proceed; the browser waits for history loading before allowing a new action and the backend enforces this across tabs. Recovery compares the saved intended fields with current provider state. Matching fields confirm the desired state without claiming which actor caused it; missing events reconcile removals. A changed ETag without the intended result becomes a terminal conflict requiring fresh inspection/review. A 412 at the actual mutation does the same. Completed receipts remain replayable without external calls. Request and event locks serialize the single-worker service.

Provider contracts are tested through HTTP callers, including lost edit/delete responses, service restart, all-day/invitation blocks and a change between pre-read and PATCH. Browser fixtures exercise history readiness, edit preview/confirmation, reload recovery and removal confirmation. Real Google/Microsoft mutations and Graph If-Match enforcement remain live acceptance checks after account authorization; fixtures do not establish provider behavior.

Email actionability uses the selected main model through an isolated tool-free runtime completion; see [Agenda contract](agenda-contract.md#email-actionability). Gmail access additionally permits exact metadata-only thread reads under the existing explicit read-only mail grant. Disconnect removes source-owned encrypted derived decision settings; no provider message is modified.
